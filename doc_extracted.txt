SIH1557 technical mechanism report
Build-level design for mining-dumper tyre intelligence
0. Design decision
Build three explainable intelligence services around one event-driven tyre data model:
Vision service: image → damage presence/type/location/severity.
Risk service: telemetry + vision + history → Low/Medium/High failure risk with reasons.
Hotspot service: GPS/IMU + damage/failure outcomes → exposure-normalized mine-road risk map.
Do not train a claimed time-to-failure model for the hackathon. A failure-time model needs repeated observations linked to the same tyre and a defined event endpoint. Mining studies do provide precedents for proportional-hazard reliability modelling and useful-life prediction, but that does not create the required public longitudinal dataset for this prototype[1][2]. Use fuzzy risk as decision support, not as a calibrated probability of failure.
Commercial systems already cover much of the monitoring perimeter: pressure/temperature, GPS, alerts, analytics, fleet integration and severity maps[3][4]. TOMS also covers inspection images, tyre work, rotations, end-of-life changes, TPMS integration and predictive analytics[5]. The defensible prototype contribution is therefore the transparent fusion mechanism and deployable interfaces, not a claim that each component is new.

2. Sensor and IIoT mechanism
The practical architecture is:
TPMS / IMU / GPS / payload-CAN → edge gateway → MQTT → backend API → time-series + relational DB → analytics → dashboard.
Mining IIoT research emphasizes interoperability and the difficulty caused by fragmented vendors, communication, data-management and security infrastructure[6].
2.1 Recommended prototype hardware
Pressure/temperature: real TPMS sensor if available; otherwise a laptop/Raspberry Pi simulator. Internal sensors are preferable because the objective is actual chamber pressure and temperature; commercial mining systems use internal readings and integrate with fleet systems[3].
IMU: MPU-6050/ICM-20948 for the demonstrator; sample at 50–100 Hz. A mine-vehicle study showed that a small number of robust accelerometer/gyroscope sensors can reconstruct stress signals and estimate accumulated damage, while speed influence remains an unresolved issue[7].
GPS: smartphone GNSS or USB GNSS at 1–10 Hz. Use map matching only after the raw track is stored.
Payload/speed: simulator initially; real deployment should read the dumper’s authorised CAN/J1939 or fleet API rather than splice into safety-critical controls.
Edge: Raspberry Pi 5 or industrial PC for gateway; ESP32 only for low-rate sensor acquisition.
Network: BLE/RS-485 locally, Wi-Fi in a controlled demo, 4G/5G for mine backhaul. Use LoRaWAN only for low-rate sparse data, not raw IMU streams.
Protocol: MQTT with QoS 1, retained device configuration, local buffering and replay after link loss.
2.2 MQTT topics
mine/{mine_id}/truck/{truck_id}/tyre/{tyre_id}/telemetry
mine/{mine_id}/truck/{truck_id}/imu
mine/{mine_id}/truck/{truck_id}/gps
mine/{mine_id}/tyre/{tyre_id}/inspection
mine/{mine_id}/alerts
2.3 Minimum edge processing
At the edge: timestamp synchronization, unit conversion, range checks, missing-value flags, IMU filtering, impact-event extraction and local pressure-loss alarms. Send both raw summary and derived event; do not discard raw values needed for later audit.

4. Temperature prediction mechanism
4.1 Why not FE in the 36-hour build?
The strongest mechanistic OTR work uses a rubber heat-generation formulation, heat conduction and boundary conditions within a finite-element thermal model[9]. It is useful for offline calibration, but needs tyre geometry, material parameters, heat-transfer coefficients and validation sensors. Use it as the scientific rationale, not the live prototype model.

5.2 Feature pipeline
inspection tread depth + tyre hours + position + payload + speed
+ TKPH + temperature excursions + pressure history + road score
→ aggregate by tyre and time window
→ calculate wear rate
→ regression/gradient boosting baseline
→ wear-rate band and projection
Use robust linear regression first. If at least 30–50 tyre-level labelled histories exist, compare gradient boosting. Use tyre ID as a grouped split to prevent leakage.
5.3 Why not ANFIS/RUL now?
Survival analysis can model time to an observed removal/failure event, but requires censoring information and longitudinal event histories. A mining study used proportional hazards and found ambient temperature affected reliability and mean residual life[1]. A recent mining tyre study reported strong tread-depth influence and a GRNN–firefly hybrid model, but its reported performance is site-specific and does not substitute for cross-site validation[2]. Use those as future benchmarks, not as a reason to deploy a black-box model without data.

6. Computer vision: image → damage/type/location/severity
6.1 Model comparison
Public image evidence is mostly passenger-car/bike domain. TyreNet contains 1,698 images, with 866 defective and 832 good images, collected at service stations and licensed CC BY 4.0[10]. A public project uses Mask R-CNN and separate models for defect, sidewall, tread and wear, but it is not evidence of mining-tyre generalisation[11]. Mining-specific work describes fender-mounted continuous imaging and hazards such as embedded objects, but the retrieved summary provides limited reproducible benchmark detail[12].
6.2 Chosen mechanism
Use YOLO transfer learning for detection plus a small severity classifier.
image
→ crop/resize/normalise
→ quality check (blur, darkness, tyre visible)
→ YOLO: damage box + class + location
→ ROI crop
→ severity classifier/rule layer
→ inspection record + confidence + recommendation
Classes:
damage_type = cut | crack | puncture | embedded_object | tear | abrasion | unknown
location = tread | shoulder | sidewall | bead | unknown
severity = minor | moderate | severe
If the existing images only say normal versus damaged, do not invent type/severity labels. Train the binary model and create staged, manually labelled images for the additional taxonomy.
6.3 Severity without cut-depth measurement
Use ordinal visual features:
Minor: small localised discontinuity; no visible structural exposure; no obvious deformation; no pressure loss.
Moderate: longer/deeper-looking crack or cut, repeated branching, visible embedded object, shoulder/sidewall involvement, or persistent defect across inspections.
Severe: large open tear, exposed reinforcement, bead damage, major sidewall deformation, rapidly increasing area, or damage accompanied by pressure loss/thermal abnormality.
These are operational labels, not millimetres. Start with a human-defined rubric and have two reviewers label a calibration set. For the demo, combine model confidence with image-derived features such as box area fraction, elongation, edge length, contrast, location and repeated detection. Do not claim structural depth or failure probability from RGB alone.

7. Fuzzy failure-risk engine
7.1 Why Mamdani is the correct prototype choice
Use a small Mamdani fuzzy inference system rather than ANFIS. A Mamdani system works with expert rules, is transparent, does not require failure labels, and supports explanations. ANFIS learns membership/rule parameters from labelled outcomes; without real tyre failures it will overfit synthetic labels and create false precision. Fuzzy predictive-maintenance studies show the general pattern: historical/knowledge-based inputs are mapped to linguistic variables and defuzzified into failure likelihood[13].
7.2 Inputs
Keep the first version to six risk dimensions:
thermal_stress: temperature level + temperature slope + positive residual;
pressure_stress: pressure deviation + loss rate;
tkph_stress: current TKPH/rated TKPH + exceedance minutes;
damage_stress: severity and location;
wear_stress: wear projection / tread remaining;
impact_stress: recent exposure-normalized impact burden.
Payload, speed, tyre age and operating history enter through these features. This avoids an unmanageable 10-input rule base.
7.3 Membership functions
Normalize each variable to 0–100 or 0–1. Use triangular/trapezoidal functions:
pressure_stress: normal (0–25), low (15–60), critical (50–100)
thermal_stress: normal (0–30), elevated (20–70), critical (60–100)
tkph_stress: normal (0–40), high (30–80), excessive (70–100)
damage_stress: none (0), minor (10–35), moderate (30–70), severe (65–100)
wear_stress: low (0–40), medium (30–75), high (65–100)
impact_stress: low (0–35), medium (25–70), high (60–100)
output risk: low (0–35), medium (25–70), high (60–100)
7.4 Rules
Use monotonic safety rules, for example:
IF pressure_stress is critical THEN risk is high
IF thermal_stress is critical THEN risk is high
IF damage_stress is severe THEN risk is high
IF damage_stress is moderate AND pressure_stress is elevated THEN risk is high
IF tkph_stress is excessive AND thermal_stress is elevated THEN risk is high
IF wear_stress is high AND thermal_stress is elevated THEN risk is high
IF impact_stress is high AND damage_stress is moderate THEN risk is high
IF two or more of {thermal, pressure, TKPH} are elevated THEN risk is medium/high
IF all stresses are normal AND no damage THEN risk is low
7.5 Inference and explanation
Fuzzification: convert numeric values to membership degrees.
Rule firing: calculate AND as minimum or product.
Aggregation: take maximum contribution for each output class.
Defuzzification: centroid of aggregated output membership function.
Decision: score 0–100 plus label.
Explanation: return the top three firing rules and raw values.
{
  "risk_score": 82,
  "risk_label": "HIGH",
  "reasons": [
    "TKPH is 1.18 times the rated value",
    "temperature is rising despite reduced speed",
    "moderate sidewall cut plus pressure loss"
  ],
  "recommended_action": "stop-and-inspect before next loaded cycle"
}
The score is not a calibrated probability unless validated against confirmed failures. The dashboard must display risk_score, risk_label, reasons, and data_quality separately.

8. Geographical damage-hotspot engine
8.1 Event detection
From IMU:
remove gravity using orientation estimate or high-pass filtering;
calculate resultant acceleration;
detect peaks above threshold with refractory period;
calculate peak g, jerk, duration and speed;
attach nearest GPS point;
assign event to road segment.
A mine-vehicle study used accelerometer/gyroscope data, coherence/LASSO signal selection, ARX stress estimation and rainflow damage accumulation; it also used accumulated damage to estimate road condition, while noting speed effects still needed work[7].
8.2 Map matching
For the hackathon, create a mine-road GeoJSON with segment IDs. Map each event to the nearest segment within a tolerance. Store both raw coordinates and assigned segment.

8.4 Distinguish hotspot types
Impact hotspot: high exposure-normalized IMU event rate; no damage outcome required.
Damage hotspot: high confirmed image/inspection damage rate per truck-km.
Failure hotspot: high confirmed removal/failure rate per truck-km.
A road can be an impact hotspot but not a failure hotspot. A thermal tyre hotspot is different: it is a tyre-state event, not a geographic cluster.
8.5 Algorithms
Start with road-segment scoring. Add DBSCAN only to discover unsegmented clusters. KDE is useful for smooth visual density but still needs exposure correction. Getis-Ord Gi* and spatial autocorrelation are future additions requiring enough events and stable spatial units. Transport hotspot research similarly shows that exposure-normalized/distribution-aware methods outperform frequency-only baselines[14].

14. Hour-by-hour build plan
Final implementation choice
The build should use: rolling TKPH + first-order temperature state model + robust wear-rate regression + YOLO transfer learning with ordinal severity + road-segment hotspot rates normalized by truck-km + Mamdani fuzzy risk. This combination is simpler than FE thermal simulation, deep survival models, ANFIS or vision transformers, but preserves the mechanisms that matter: workload, thermal state, pressure, visible damage, cumulative wear, impact exposure and tyre history. The product’s strongest scientific claim should be that it provides explainable, multimodal maintenance prioritization; its weakest claims—validated failure probability, precise cut depth and time-to-failure—should remain future research until CIL supplies longitudinal tyre-level outcomes.
